# P03A-03 fuel migration progress

Status: in progress. Source baseline is `860c3ec04dac73bc10d6aba65798aff31887fdbb` with uncommitted changes; the commit alone does not identify the inspected source.

The active `MotoVault` fuel entry opens `FuelSheet` from `Sheets.kt`. Its current UI owns entry state, validation, calculations and construction of the persisted log. The common `FuelEfficiencyUseCase` separately computes economy. `OwnershipForms.kt` contains a `FuelDialog` with an edit path through `replaceFuelLog`, but repository source search finds no caller for `FuelDialog`; the active `HistoryScreen` provides delete but no edit action. P03A-03 must provide and verify a real fuel edit flow, not claim an unused dialog as working behavior.

The migration must preserve existing serialized fields, numeric semantics, original record metadata, coordinator revision/conflict behavior, draft behavior, failed-save behavior and Undo. The active v3 prototype must be extended before adding a visible edit flow. No fuel migration implementation or device acceptance is claimed by this initial trace.

## Calculation extraction

`FuelEntryRules` now owns the existing amount/litres calculation and validation priority, returning typed issues. The sheet maps these outcomes to localized messages and uses a typed mode. The Android unit suite and two focused iOS simulator domain tests passed; no app runtime check of this extraction is claimed. The rules intentionally retain the current behavior for now, including its existing limits and validation order.

Further source inspection found that the active sheet constructs a `RideLog` and copies state directly rather than calling `VaultState.logFuel`. Unlike that older workflow, it does not explicitly update `lastFuelOdometer` or `economy` and does not apply its date and amount validation. Resolve these differences with compatibility and regression evidence during the migration; the calculation extraction alone does not satisfy the feature task.

## Save compatibility adapter

The sheet now emits a fuel request. An injected adapter maps it into the existing `VaultState` and `RideLog` representation before the root uses the same revision-aware writer. This is a transitional adapter because the persisted vault model is still UI-owned. It preserves the legacy record fields and recent-place behavior; no stored schema was changed.

An initial round-trip test failed because `VaultState.decode` recomputes `lastFuelOdometer` and `economy` while the prior active save path left them stale. The adapter now uses the same existing economy calculation immediately after adding a record, so its in-memory snapshot and decoded snapshot agree. The Android unit suite and focused iOS rule and adapter tests passed after the correction, including synthetic legacy-field preservation, a full-tank economy example and a serialize/decode round trip. No old archive fixture, app save/Undo runtime, or physical-device verification is claimed. Fuel validation, edit, conflicts and broader feature boundaries remain open.
